What is a Network Source of Truth?

  • Defines the intended state of the network as structured data
  • A single consistent data set — not spreadsheets and Visio diagrams
  • The authoritative reference that drives network automation
  • Not a static CMDB — an active platform with APIs, webhooks, and event streams
A network source of truth defines what the network should look like as structured, API-accessible data. It's the shift from describing your network in documents to modeling it in a system that can drive automation. NetBox is the most popular implementation of this concept.

The Solution

Automated Failover Architecture

NetBox Circuit → offline
EDA Webhook → rulebook
Step 1: Failover Query NetBox, discover backup, update SoT
Step 2: Router Config Push routing via cisco.ios
Step 3: Report HTML report → GitHub Pages

Backup discovery is dynamic — all circuits tagged dd present at both sites are candidates, selected by highest committed bandwidth. No hardcoded backup mappings.

Here's the full architecture. When a circuit status changes to offline in NetBox, an event rule fires a webhook to Event-Driven Ansible. EDA evaluates the rulebook condition and launches the Circuit Failover Workflow on Automation Controller. The workflow has three steps: update the source of truth, push router config, generate the incident report. Backup discovery is dynamic — no hardcoded mappings.

Under the Hood

EDA Rulebook — The Glue

- name: NetBox Circuit Failover
  hosts: all
  sources:
    - ansible.eda.webhook:
        host: 0.0.0.0
        port: 5000

  rules:
    - name: Circuit failure detected
      condition: >
        event.payload.object_type == "circuits.circuit" and
        event.payload.data.status.value in ["offline", "failed"]
      action:
        run_workflow_template:
          name: "Circuit Failover Workflow"
          organization: "Webinar"
          job_args:
            extra_vars:
              failed_circuit: "{{ event.payload.data.cid }}"
This is the entire EDA rulebook. It listens for NetBox webhook events, checks if a circuit went offline or failed, and launches the failover workflow on Automation Controller — passing the circuit ID as an extra variable. That's it. Eight lines of condition and action logic.

Under the Hood

Dynamic Backup Discovery

# Query circuits at both sites, find common ones, pick the best
- name: Query dd-tagged circuits at A-side site
  ansible.builtin.set_fact:
    a_site_circuits: >-
      {{ query('netbox.netbox.nb_lookup', 'circuits',
               api_filter='site_id=' ~ a_side_site.id ~ ' tag=dd') }}

- name: Build backup candidate list
  ansible.builtin.set_fact:
    backup_candidates: >-
      {{ a_site_circuits
         | selectattr('id', 'in', z_circuit_ids)
         | rejectattr('id', 'eq', primary.id)
         | list }}

- name: Select best backup (highest commit rate)
  ansible.builtin.set_fact:
    backup: >-
      {{ backup_candidates
         | sort(attribute='commit_rate', reverse=true)
         | first }}
Here's the key logic from the failover playbook. No hardcoded backup mappings. It queries NetBox for all circuits tagged 'dd' at both sites, finds the ones that exist at both ends, excludes the failed one, and picks the backup with the highest committed bandwidth. If you add a new circuit to NetBox tomorrow, the automation discovers it automatically.

Under the Hood

Gateway Derivation from NetBox

NetBox Data Model

Circuit (IPLC-GB-AT-PRI)
  └─ Termination (A-side)
       └─ Cable → Device Interface
            └─ IP: 172.16.0.2/24
  • Circuit terminations are cabled to router interfaces in NetBox
  • Each interface has an IP address assigned
  • The gateway is derived, not stored

Gateway Logic

# IP on the interface
172.16.0.2/24
  → network: 172.16.0.0/24
    → first host: 172.16.0.1 ← gateway

# Router config generated:
no ip route 0.0.0.0/0 172.16.0.1  # old
ip route 0.0.0.0/0 172.16.1.1    # new
  • Subnet's first usable host = provider gateway
  • Works for point-to-point links (.1 = provider, .2 = customer)
This is how the automation knows which gateway to remove and which to add — without any hardcoded IPs. Each circuit termination in NetBox is cabled to a router interface. That interface has an IP address. The playbook takes that IP, extracts the subnet, and derives the gateway as the first usable host — because on a point-to-point link, .1 is the provider side and .2 is our router. So the entire router config — which route to remove, which to add — comes directly from the NetBox data model. Change a cable or IP in NetBox, and the next failover automatically uses the right gateways.

Closing the Loop

MCP — Model Context Protocol

  • An open standard for connecting AI assistants to external systems
  • AI sees self-describing tools — not raw API endpoints
  • Works across models and clients — not vendor-locked
  • Think: Ansible modules for AI — same capability as raw API, but with a consistent interface, scoped permissions, and built-in discovery

NetBox MCP Server

Read-only access to network data: sites, circuits, devices, IPs.

Scoped with a readonly API token.

AAP MCP Server

Query job history, workflow status, job events, host summaries.

Launch and monitor automation workflows.

MCP is an open standard for connecting AI assistants to external data sources. Think of it as Ansible modules for AI — same underlying capability as raw API access, but with a consistent interface, scoped permissions, and built-in discovery. Both NetBox and Ansible Automation Platform have MCP servers.

Closing the Loop

Why MCP, Not Just the API?

What MCP Adds

  • Tool-level permissioning — operator approves each action visibly
  • Multi-system correlation — AAP + NetBox in one conversation, no glue code
  • Standardized interface — works in IDEs, chatbots, agent frameworks

The Honest Take

  • MCP doesn't make anything possible that wasn't before
  • It makes it governable — scoped tokens, visible actions, audit trail
  • Same argument as Ansible modules vs. raw SSH — same capability, better interface
Let's be honest about what MCP is and isn't. It doesn't make anything possible that wasn't before — you can always just use the API directly. What it adds is governance: scoped permissions, visible tool invocations the operator can approve or deny, and a standard interface that works across different AI clients. It's the same argument as Ansible modules vs raw SSH — same capability, but a consistent, governed interface that scales better.
