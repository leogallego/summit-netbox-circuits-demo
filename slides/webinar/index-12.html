Context

Network Source of Truth — NetBox

What is a Network SoT?

  • Defines the intended state of the network as structured data
  • A single consistent data set — not spreadsheets and Visio diagrams
  • The authoritative reference that drives network automation
  • Not a static CMDB — an active platform with APIs, webhooks, and event streams

Why NetBox?

  • Comprehensive data model — from ASNs to VPNs and everything in between
  • API & integration first — REST, GraphQL, Event Streams, Webhooks
  • Massive extensibility — Plugins, Device Types, Custom Scripts & Fields
  • 15K+ GitHub stars · 1000s of companies in production
A network source of truth models your intended network state as structured, API-accessible data. NetBox is the most popular implementation — 15,000 GitHub stars, thousands of companies in production. The key for today: when something changes in NetBox, it can notify external systems immediately via webhooks. That's the trigger for everything you're about to see.

The Solution

Automated Failover Architecture

NetBox Circuit → offline
EDA Webhook → rulebook
Step 1: Failover Discover backup, update SoT
Step 2: Config Push routing via cisco.ios
Step 3: Report HTML → GitHub Pages

The EDA rulebook is 8 lines of logic: listen for NetBox webhook, check if circuit went offline, launch the workflow. The circuit ID flows straight from the NetBox payload into the workflow as an extra variable.

Backup discovery is dynamic: all circuits tagged dd present at both sites are candidates, selected by highest committed bandwidth. No hardcoded backup mappings.

Here's the automated version. Circuit goes offline in NetBox, webhook fires to EDA, EDA launches a three-step workflow. Step one discovers the backup dynamically from NetBox — no hardcoded mappings. Step two pushes router config. Step three generates and publishes the report. The EDA rulebook that connects NetBox to the workflow? Eight lines of YAML. The backup discovery logic queries all circuits at both sites, excludes the failed one, and picks the best by bandwidth. Add a new circuit to NetBox tomorrow and it's automatically discovered. MCP — Model Context Protocol

  • Open standard connecting AI to external systems
  • Self-describing tools, scoped permissions
  • Think: Ansible modules for AI

NetBox MCP

Read-only network data

AAP MCP

Job history + workflows

The automation handled the 2am fire drill. But at 9am, someone needs answers. Was the right backup activated? Should we fail back? Today that means three different UIs and manual correlation. MCP — Model Context Protocol — is an open standard that connects AI assistants to external systems. Think Ansible modules for AI: same capability as raw API, but governed, discoverable, and scoped. Both NetBox and AAP have MCP servers. Let me show you what that looks like.

Closing the Loop

The Operator's Investigation

Ask "What was the latest circuit incident?"
MCP Queries AAP job history + NetBox circuit status simultaneously. Returns a cross-system incident summary.
Ask "Is the report timeline still accurate?"
MCP Fetches the published report, correlates against actual AAP job durations and live NetBox state.
Ask "Confirm the site coordinates in NetBox are correct."
MCP Queries NetBox sites API, returns regions and coordinates for verification.
This is what we actually did preparing for this presentation. Natural language questions, MCP queries both AAP and NetBox simultaneously, correlated answers come back. No switching between UIs, no API knowledge required. The operator gets a complete picture without touching a single dashboard.
