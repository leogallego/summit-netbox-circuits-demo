Context

Network Source of Truth — NetBox

What is a Network SoT?

  • The intended state of the network as structured data
  • A single consistent data set — not spreadsheets and Visio diagrams
  • An active platform with APIs, webhooks, and event streams that drives automation

Why NetBox?

  • Comprehensive data model — from ASNs to VPNs, circuits to cables
  • API & integration first — REST, GraphQL, Webhooks
  • 15K+ GitHub stars · 1000s in production
  • Maintained by NetBox Labs — commercial steward of the OSS project
A network source of truth models your intended network state as structured, API-accessible data. NetBox is the most widely adopted implementation — 15,000 GitHub stars, thousands of companies in production, maintained by NetBox Labs. The key for today: when something changes in NetBox, it fires webhooks immediately. That's the trigger for everything you're about to see.

The Solution

Automated Failover Architecture

NetBox Circuit → offline
EDA Webhook → rulebook
Step 1: Failover Discover backup, update SoT
Step 2: Config Push routing via cisco.ios
Step 3: Report HTML → GitHub Pages

Everything is derived from NetBox data. Backup circuit selection, gateway IPs, router targets — no hardcoded values anywhere. Change a cable or IP in NetBox and the next failover uses the right config automatically.

Here's the automated version. Circuit goes offline in NetBox, webhook fires to EDA, EDA launches a three-step workflow. Step one discovers the backup dynamically from NetBox and updates the source of truth. Step two pushes router config — the gateway IPs are derived from the circuit termination cabling in NetBox, not hardcoded. Step three generates and publishes the incident report. Nothing is hardcoded. Let me show you the code.

Under the Hood

EDA Rulebook — The Glue

- name: NetBox Circuit Failover
  hosts: all
  sources:
    - ansible.eda.webhook:
        host: 0.0.0.0
        port: 5000

  rules:
    - name: Circuit failure detected
      condition: >
        event.payload.object_type == "circuits.circuit" and
        event.payload.data.status.value in ["offline", "failed"]
      action:
        run_workflow_template:
          name: "Circuit Failover Workflow"
          organization: "Webinar"
          job_args:
            extra_vars:
              failed_circuit: "{{ event.payload.data.cid }}"
This is the entire rulebook — the complete file, not a snippet. Listen for webhooks, check if a circuit went offline or failed, launch the workflow, pass the circuit ID. Eight lines of logic connecting NetBox to Automation Controller.

Under the Hood

From NetBox Data to Router Config

Backup Discovery

# All dd-tagged circuits at both sites
backup_candidates:
  {{ a_site_circuits
     | selectattr('id', 'in', z_circuit_ids)
     | rejectattr('id', 'eq', primary.id)
     | list }}

# Best = highest committed bandwidth
backup:
  {{ backup_candidates
     | sort(attribute='commit_rate',
            reverse=true)
     | first }}

Gateway Derivation

# NetBox: Circuit → Termination
#   → Cable → Interface → IP
# IP: 172.16.0.2/24
#   → subnet: 172.16.0.0/24
#     → first host = gateway

# Generated router config:
no ip route 0.0.0.0/0 172.16.0.1
ip route 0.0.0.0/0 172.16.1.1

Point-to-point links: .1 = provider, .2 = customer router

Two key pieces. On the left — backup discovery. Query all circuits tagged 'dd' at both sites, find the ones present at both ends, exclude the failed one, pick the best by bandwidth. Add a circuit to NetBox tomorrow, it's automatically discovered. On the right — gateway derivation. Each circuit termination is cabled to a router interface in NetBox. That interface has an IP. The playbook derives the gateway from the subnet — first usable host. So the router config comes entirely from the NetBox data model. No hardcoded IPs, no mapping tables. MCP — Model Context Protocol

  • Open standard connecting AI to external systems
  • Self-describing tools with scoped permissions
  • Think: Ansible modules for AI

NetBox MCP

Read-only network data

AAP MCP

Job history + workflows

The automation handles the 2am fire drill. But at 9am, someone walks in and needs answers. Today that means three different UIs and manual correlation. MCP — Model Context Protocol — is an open standard that connects AI to external systems. Think Ansible modules for AI: same capability as raw API, but governed, discoverable, and scoped. Both NetBox and AAP have MCP servers. In the demo, you'll see the failover run, then immediately see an operator investigate it using natural language. Two demos, one flow.

Beyond the Demo — What Else Can You Build?

Monitoring Triggers

  • LogicMonitor, Zabbix, Prometheus detect link down
  • SNMP trap or API call updates NetBox automatically
  • Same EDA pipeline — no code changes

Incident Tracking

  • Auto-create GitHub/ServiceNow issue on failover
  • Attach report link when published
  • Operator closes issue after failback

Failback & Beyond

  • Provider restores primary → automated failback
  • Multi-circuit, multi-site failover
  • Compliance checks post-failover

The architecture is the same. NetBox as trigger → EDA as router → AAP as executor → MCP for investigation. Swap the playbooks, scale the pattern.

Everything you just saw is one instance of a pattern. Replace the manual NetBox click with LogicMonitor or Zabbix — same EDA pipeline, no code changes. Add a GitHub issue creation step to the workflow for incident tracking — we've already prototyped this. Automate the failback when the provider restores the primary. Run compliance checks after every failover. The architecture stays the same: NetBox triggers, EDA routes, AAP executes, MCP investigates. You just swap the playbooks.
