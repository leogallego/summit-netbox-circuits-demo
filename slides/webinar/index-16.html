Here's the automated version of those 45 minutes. Circuit goes offline in NetBox, event rule fires a webhook to EDA, EDA evaluates the condition and launches a three-step workflow on Automation Controller. Step one queries NetBox and discovers the backup dynamically. Step two pushes router config. Step three generates and publishes the incident report. No hardcoded backup mappings — it discovers the best candidate automatically. Let me show you the code.

Under the Hood

EDA Rulebook — The Glue

- name: NetBox Circuit Failover
  hosts: all
  sources:
    - ansible.eda.webhook:
        host: 0.0.0.0
        port: 5000

  rules:
    - name: Circuit failure detected
      condition: >
        event.payload.object_type == "circuits.circuit" and
        event.payload.data.status.value in ["offline", "failed"]
      action:
        run_workflow_template:
          name: "Circuit Failover Workflow"
          organization: "Webinar"
          job_args:
            extra_vars:
              failed_circuit: "{{ event.payload.data.cid }}"
This is the entire rulebook — not a snippet, the complete file. Listen for webhooks, check if a circuit went offline or failed, launch the workflow. The circuit ID flows straight from the NetBox payload into the workflow as an extra variable. Eight lines of logic.

Under the Hood

Dynamic Backup Discovery

# Query circuits at both sites, find common ones, pick the best
- name: Query dd-tagged circuits at A-side site
  ansible.builtin.set_fact:
    a_site_circuits: >-
      {{ query('netbox.netbox.nb_lookup', 'circuits',
               api_filter='site_id=' ~ a_side_site.id ~ ' tag=dd') }}

- name: Build backup candidate list
  ansible.builtin.set_fact:
    backup_candidates: >-
      {{ a_site_circuits
         | selectattr('id', 'in', z_circuit_ids)
         | rejectattr('id', 'eq', primary.id)
         | list }}

- name: Select best backup (highest commit rate)
  ansible.builtin.set_fact:
    backup: >-
      {{ backup_candidates
         | sort(attribute='commit_rate', reverse=true)
         | first }}
Here's the backup discovery logic. Query NetBox for all circuits tagged 'dd' at both sites, find the ones present at both ends, exclude the failed one, sort by committed bandwidth, pick the best. No hardcoded mappings. Add a new circuit to NetBox tomorrow and the automation discovers it automatically. Now let's watch it run.

Closing the Loop

MCP — Model Context Protocol

  • An open standard for connecting AI assistants to external systems
  • AI sees self-describing tools — not raw API endpoints
  • Works across models and clients — not vendor-locked
  • Think: Ansible modules for AI — same capability as raw API, but with scoped permissions, visible actions, and built-in discovery

NetBox MCP Server

Read-only access to network data: sites, circuits, devices, IPs.

Scoped with a readonly API token.

AAP MCP Server

Query job history, workflow status, job events, host summaries.

Launch and monitor automation workflows.

MCP — Model Context Protocol — is an open standard for connecting AI assistants to external systems. Think of it like Ansible modules for AI: you could always SSH into a box directly, but modules give you a governed, consistent, discoverable interface. Same idea here. Both NetBox and AAP have MCP servers. The operator doesn't need to know the API — they ask questions in natural language, and MCP routes the queries to the right system with scoped permissions.
